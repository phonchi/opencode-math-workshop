# 產線故障預測：模型訓練與上線可行性報告

- 資料：`data/line_faults.csv`（900 筆、6 個感測特徵、標籤 `fault`）
- 重現指令：`uv run python train_fault_model.py`
- 明細指標：`notes/line_fault_metrics.csv`
- 圖：`figs/fault_model_timeline.png`、`figs/fault_model_validation.png`

## 結論

**目前不能上線。** 問題不在模型演算法，而在資料本身無法支持「未來故障能否被偵測」的驗證。

三個關鍵事實：

1. 71 個故障全部集中在 `record_id` 1–111，之後 789 筆全部正常；這看起來是**同一次事件**（很可能是開機／暖機／調機階段），不是多次獨立故障。
2. 用隨機切分會得到 AUC 0.93–0.96 的漂亮數字，但訓練集與測試集共享同一次事件，這是時間洩漏造成的樂觀估計。
3. 若把 `record_id` 當特徵，AUC 高達 0.994–0.999，幾乎等於直接把答案餵給模型。這證明資料的「時間順序」本身就能完美區分多數樣本。

因此，現在訓練出的模型最可能學到的是「資料開頭那段時期」或「暖機狀態」，而不是可泛化的故障機制。

## 資料觀察

| 區間（record_id） | 筆數 | 故障率 |
|---|---:|---:|
| 1–50 | 50 | 1.00 |
| 51–100 | 50 | 0.38 |
| 101–150 | 50 | 0.04 |
| 151–200 | 50 | 0.00 |
| 201–900 | 700 | 0.00 |

其他觀察：

- 故障率 71/900 = 7.9%，類別不平衡。
- 沒有缺失值，也沒有特徵完全重複的資料。
- 故障時平均溫度 70.3°C，正常時 64.6°C；溫度與 `fault` 的相關係數 +0.38。
- 故障時平均振動 2.60 mm/s，正常時 3.05 mm/s；**故障時振動反而較低**，與常見的「振動升高代表異常」直覺相反。
- 溫度與時間順序的相關係數為 −0.22；溫度同時與「早期」和「故障」重疊，模型無法分辨是溫度造成故障，還是只是早期狀態。

## 驗證方式

這裡刻意比較四種切分：

1. **隨機 5-fold**：一般教學常用，但此資料有時序，會高估。
2. **加入 `record_id` 的隨機 5-fold**：示範洩漏。
3. **時間切分**：前 60% 訓練、後 40% 測試。測試期完全沒有故障。
4. **故障期後上線模擬**：前 200 筆訓練（含全部 71 個故障），後 700 筆測試（全正常）。

隨機切分結果：

| 模型 | AUC | PR-AUC | 最佳 F1 | Precision | Recall |
|---|---:|---:|---:|---:|---:|
| Logistic regression | 0.961 | 0.718 | 0.637 | 0.52 | 0.82 |
| Random forest | 0.935 | 0.509 | 0.567 | 0.47 | 0.72 |
| Hist. gradient boosting | 0.931 | 0.560 | 0.558 | 0.52 | 0.61 |

加入 `record_id` 後：

| 模型 | AUC | PR-AUC |
|---|---:|---:|
| Logistic regression | 0.999 | 0.992 |
| Random forest | 0.998 | 0.986 |
| Hist. gradient boosting | 0.994 | 0.981 |

AUC 從 0.93–0.96 跳到 0.99 以上，不是模型變強，而是 `record_id` 直接編碼了「是否在故障期」。

時間切分的結果如下。門檻是在訓練集上取可達 90% recall 的機率門檻，然後套到測試集；因為測試集沒有故障，只能計算**誤報率**，無法計算召回率或 AUC。

| 模型 | 後 40% 測試期誤報 | 故障期後 700 筆誤報 |
|---|---:|---:|
| Logistic regression | 28/360（7.8%） | 63/700（9.0%） |
| Random forest | 5/360（1.4%） | 38/700（5.4%） |
| Hist. gradient boosting | 1/360（0.3%） | 36/700（5.1%） |

Hist. gradient boosting 的誤報最少，但這**不代表**它抓得到故障：測試期一個故障都沒有，沒有任何證據顯示它能召回未來的故障。低誤報也可能只是因為它把後期資料一律判正常。

## 為什麼不能上線

1. **只有一次故障事件。** 所有正樣本都在連續的 111 筆內，沒有獨立事件可供驗證。隨機切分只是把同一次事件拆到訓練與測試兩邊。
2. **時間洩漏。** `record_id` 與標籤幾乎完全對應；即使不放 `record_id`，溫度等特徵也隨時間漂移，隨機切分仍會高估。
3. **標籤語意不明。** 前 50 筆 100% 故障，之後逐漸降為 0，這比較像開機／暖機／調機的暫態，而不是隨機發生的設備故障。模型可能只是在偵測「暖機中」。
4. **特徵方向不合理。** 故障時振動較低，與一般預測性維護的物理直覺相反；需要確認感測器校正、單位與標籤定義。
5. **沒有營運成本定義。** 71 個正樣本下，門檻稍微變動就會大幅改變誤報量；沒有定義漏報與誤報的成本，無法選出可上線的操作點。

## 上線前需要補的資料與驗證

1. 收集 **至少 3–5 次獨立故障事件**，跨不同時間、機台、批號與產品；保留 `timestamp`、`event_id`、故障原因、維修紀錄。
2. 使用**時間切分或 rolling-origin 驗證**，必要時以事件為單位分組；不要用隨機切分。
3. `record_id` 只能當中介資料，**不可當特徵**。
4. 先定義營運目標：可接受漏報率、每週可接受誤報次數、告警處理成本；再選門檻並做機率校準。
5. 上線前先跑 shadow mode（只預測、不告警），累積至少數個月的實際表現；同時監控特徵漂移。
6. 若故障標籤仍然稀少，可考慮無監督異常偵測，但仍然必須用**未來的獨立故障事件**驗證。

## 目前可交付的內容

`train_fault_model.py` 已包含可重現的資料載入、三種模型、隨機切分、時間切分、洩漏示範、指標輸出與圖表。這些結果適合當作「資料品質與驗證設計」的診斷，不適合當作上線模型。

建議下一步不是調模型，而是先補齊獨立故障事件與時間戳，再重新做時間基礎的驗證。
