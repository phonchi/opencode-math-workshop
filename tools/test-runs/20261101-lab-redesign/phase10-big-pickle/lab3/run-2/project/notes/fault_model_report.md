# 產線故障預測：模型與上線可行性評估

資料：`data/line_faults.csv`（900 筆、6 個感測特徵、標籤 `fault`）
程式：`train_fault_model.py`　圖：`figs/fault_model_diagnostics.png`

## 結論（先講重點）

**不建議直接上線。** 不是模型不夠複雜，而是這份資料的故障樣本在時間上嚴重集中，
隨機交叉驗證的分數會騙人；用「過去訓練、未來測試」的情境檢查，模型會大量誤報。

## 資料長相

- 故障率 $71/900 = 7.9\%$，類別不平衡。
- 71 筆故障**全部落在 `record_id` 1–200**，其中 69 筆在 1–100；第 201–900 筆**一筆故障都沒有**。
- `record_id` 與 `fault` 的相關係數 $-0.464$。
- 只用 `record_id` 一個特徵做隨機 CV，ROC-AUC 就有 **0.983**、PR-AUC **0.945**。
  這代表 `record_id` 幾乎可以直接「猜」到標籤，是典型的時間洩漏。

| record_id | 筆數 | 故障數 | 故障率 |
|---|---:|---:|---:|
| 1–100 | 100 | 69 | 0.69 |
| 101–200 | 100 | 2 | 0.02 |
| 201–900 | 700 | 0 | 0.00 |

## 隨機 CV 看起來很好，但不能信

5-fold 分層隨機 CV（`class_weight="balanced"`）：

| 模型 | ROC-AUC | PR-AUC | Brier |
|---|---:|---:|---:|
| Logistic regression | 0.960 | 0.716 | 0.083 |
| Random forest | 0.932 | 0.505 | 0.063 |

隨機 CV 會把「早期故障」與「後期正常」隨機混進訓練集與測試集，
模型等於同時看到未來與過去，所以分數被時間索引撐高。

## 時間切分才是上線情境

用前面時段訓練、後面時段測試：

| 訓練 | 測試 | 測試故障數 | ROC-AUC | PR-AUC | 預測為故障的筆數 |
|---|---|---:|---:|---:|---:|
| 1–100 | 101–900 | 2 | 0.880 | 0.130 | 210 |
| 1–150 | 151–900 | 0 | 無法計算 | 無法計算 | 121 |
| 1–200 | 201–900 | 0 | 無法計算 | 無法計算 | 95 |

- 測試期幾乎沒有故障，**recall 根本無法估計**；PR-AUC 掉到 0.13。
- 模型在後 700 筆正常資料上仍把 95–210 筆判成故障（門檻 0.5），
  等於每次輪班都在製造假警報。這是特徵漂移加上時間洩漏的結果。
- 特徵本身也有漂移，例如 `temp_c` 後期比前期低約 $0.47$ 個標準差、`vibration_mm_s` 高約 $0.33$ 個標準差。

## 為什麼不能上線

1. **故障樣本太少且集中**：71 筆正例，95% 信賴區間很寬；而且只代表早期工況。
2. **沒有可用的時間外驗證**：後 700 筆零故障，無法證明模型在新工況下抓得到故障。
3. **時間洩漏**：`record_id` 與標籤高度相關，任何用到時間順序的隨機切分都會高估效能。
4. **誤報成本未定義**：目前沒有漏報（FN）與誤報（FP）的成本，無法選門檻。
5. **只有單一資料來源**：`line_channels.csv`、`line_modes.csv` 與本檔沒有共同鍵，無法合併驗證。

## 要能上線，至少需要

- 補齊**跨時間、跨工況的故障樣本**（尤其 201 筆之後），讓測試期有足夠正例。
- 改用**時間序列驗證**（rolling-origin / walk-forward），不可用隨機 K-fold。
- **移除 `record_id`** 等時間索引特徵，只留上線時真的拿得到的感測值。
- 先定義成本矩陣，再依 PR 曲線選操作點；不要用 0.5。
- 上線流程先跑 **shadow mode**，監控特徵漂移與誤報率，再談自動停機。

## 建議的下一步

1. 確認 201–900 筆為何完全沒有故障：是產線真的沒故障、標註漏掉，還是資料抽取只涵蓋特定期間？
2. 取得含時間戳與故障維修紀錄的完整資料。
3. 用 walk-forward 重新評估，回報每個時段的 PR-AUC、recall、誤報率與校準。
