# 產線故障預測模型評估報告

## 結論：不建議上線

以目前的 `data/line_faults.csv` 訓練出的模型，**只能離線展示，不能直接上線**。
主要不是模型演算法不好，而是資料本身的時間結構讓「好看的驗證分數」失去意義。

## 資料

- 900 筆、6 個製程特徵（溫度、振動、壓力、流量、電流、轉速），故障 71 筆（7.9%）。
- 檔案中的列是**打亂的**；真正的時間順序要依 `record_id` 還原。
- 71 筆故障全部落在 `record_id = 1–111`，之後 789 筆**完全沒有故障**。

![fault timeline](../figs/fault_timeline.png)

也就是說，這份資料只包含**一次早期故障事件**（或開機/試車階段的異常），
不是涵蓋平時運轉與多次故障的長期紀錄。

## 評估結果

模型：標準化 + 邏輯迴歸（`class_weight="balanced"`）。

| 切分方式 | ROC-AUC | PR-AUC | 說明 |
|---|---:|---:|---|
| 隨機分層 5-fold CV | 0.961 | 0.718 | 同一段故障事件同時出現在訓練與測試，分數被高估 |
| 依連續 100 筆時間區塊分組 CV | 0.768 | 0.467 | 換到其他時間區塊就明顯變差 |
| 時間外推（前 600 筆訓練、後 300 筆測試） | 無法計算 | 無法計算 | 測試集 0 筆故障，算不出 recall |

![evaluation](../figs/evaluation_random_vs_temporal.png)

時間外推的實際行為：

- 門檻 0.5：後段 300 筆正常資料有 **11.7% 被誤報為故障**。
- 把門檻調到 CV 可達 90% recall 的 0.596：仍有 **9.3% 誤報**。
- 而且測試集沒有任何故障，**召回率完全無法驗證**。

## 為什麼隨機 CV 的 0.96 不能信

1. **時間洩漏**：故障只發生在 `record_id ≤ 111`。隨機切分會让訓練集與測試集都含這段事件，
   模型其實在學「這段時間的溫度偏高、振動偏低」，而不是學可推廣的故障機制。
2. **單一事件**：71 筆正樣本來自同一次事件，無法區分「故障特徵」與「當時的環境/製程偏移」。
3. **係數方向不合理**：模型主要靠 `temp_c`（正）與 `vibration_mm_s`（負）。
   故障通常應該伴隨振動上升，這裡卻是振動越低越像故障，比較像開機暖機階段的特徵。
4. **沒有可用的時間驗證**：真正的上線驗證應該是「用過去預測未來」，但後段沒有任何故障可測。

## 補充：其他資料集有明顯分布偏移

用同一組特徵檢查 `data/line_modes.csv`：

- 溫度、壓力、流量、電流、轉速有 **36–62%** 的列超出 `line_faults` 的 1–99 百分位範圍。
- 把模型套上去，**34% 的列會被判成故障**。
- `line_channels.csv` 的通道尺度與 `line_faults` 對不上，直接套用幾乎全判正常。

若 `line_modes` / `line_channels` 才是實際上線會遇到的資料，現在的模型**不能轉移**。

## 上線前至少要做的事

1. 收集涵蓋**多次故障、跨一段時間**的資料，且每次事件都要有清楚的標籤定義。
2. 只用**時間切分**驗證（例如 rolling-origin），不能用隨機切分。
3. 確認故障標籤的產生方式（人工通報？保養紀錄？），避免標籤本身有時間偏差。
4. 先做分布監控（特徵漂移），再談模型；門檻要依誤報/漏報成本決定。
5. 若故障樣本仍少，可先做無監督異常偵測（只用正常資料建模），但同樣需要時間外驗證。
