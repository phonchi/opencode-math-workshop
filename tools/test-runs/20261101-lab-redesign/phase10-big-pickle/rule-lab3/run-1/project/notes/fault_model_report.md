# 產線故障預測：可行性分析

## 結論

**不建議上線。** 不是模型分數不夠高，而是這份資料無法支撐「上線後仍有效」的驗證。用隨機切分得到的 AUC 0.96 是時間洩漏造成的樂觀結果；依照時間切分後，未來 789 筆完全沒有故障，無法量測召回率。把在故障期訓練的模型套到後段正常資料，誤報率仍高達 8.5%–27.8%。

## 資料與前處理

- `data/line_faults.csv`：900 筆、6 個感測特徵、標籤 `fault`。故障 71 筆，占 7.89%。
- CSV 的列順序不是時間順序，因此先依 `record_id` 排序再分析。這個排序是本次自行做的前處理決定。
- `record_id` 只用來排序與切分，沒有當成模型特徵。
- 沒有刪除任何欄位；6 個感測特徵全部使用。
- 沒有合併 `line_modes.csv` 與 `line_channels.csv`，原因見文末。

## 主要發現

### 1. 故障標籤集中在時間軸最前面

- 全部 71 筆故障都落在 `record_id` 1–111。
- `record_id` 112–900 共 789 筆，故障數為 0。
- 前 55 筆全部是故障，代表資料是從故障事件中間開始記錄，沒有故障前的正常基線。

因此 `record_id` 幾乎可以完美分離故障（把 `record_id` 當分數預測 `fault`，AUC 約 0.003，方向反過來就是接近 1）。模型很容易學到「這是資料開頭的那段時間」，而不是學到真正的故障機理。

### 2. 隨機交叉驗證的分數很好看，但不能用

以隨機分層 5-fold 交叉驗證：

| 模型 | AUC | Average Precision |
|---|---:|---:|
| Logistic regression | 0.960 | 0.716 |
| Random forest | 0.933 | 0.528 |
| Gradient boosting | 0.933 | 0.635 |

這個切分會把同一個故障事件的前後相鄰紀錄同時放進訓練集與測試集，等於讓模型偷看答案，分數不能用來估計上線表現。

### 3. 照時間切分後，無法驗證

- 用 1–111 訓練、112–900 測試：測試集有 **0 筆故障**，AUC 與召回率都無法計算。
- 用 expanding window 的 time-series CV：5 個 fold 的測試集故障數全部是 0。
- 用 1–450 訓練、451–900 測試：測試集同樣是 0 筆故障。

也就是說，這份資料只有一次故障事件，沒有第二段獨立故障可以用來驗證。

### 4. 套用到後段正常資料會產生大量誤報

以 1–111 訓練，將門檻調到故障期內召回率 90%，再套用到 112–900 的 789 筆正常資料：

| 模型 | 後段誤報筆數 | 誤報率 |
|---|---:|---:|
| Logistic regression | 100 | 12.7% |
| Random forest | 75 | 9.5% |
| Gradient boosting | 67 | 8.5% |

若直接用 0.5 當門檻，誤報率分別是 17.1%、20.2%、27.8%。這代表模型學到的邊界沒有轉移到後段資料。

### 5. 早期與後段的特徵分布本身就不一樣

| 特徵 | 故障期 1–111 平均 | 後段 112–900 平均 |
|---|---:|---:|
| temp_c | 68.31 | 64.58 |
| vibration_mm_s | 2.72 | 3.05 |
| speed_rpm | 1522.35 | 1498.77 |

故障標籤與「時段」完全糾纏。模型可能只是學到啟動期／維修期的特徵偏移，而不是可重複的故障前兆。

## 為什麼不能上線

1. **只有一次故障事件**，沒有跨事件、跨時間的獨立驗證。
2. **沒有故障前正常資料**（前 55 筆全為故障），無法訓練或驗證預警模型。
3. **沒有定義預測時間窗**。目前的 `fault` 看起來是當下狀態標籤，不是「未來 N 分鐘會故障」。若目標是預警，現在的資料格式不足。
4. **誤報成本未知**。在 789 筆正常資料上誤報 8.5%–12.7%，對產線而言很可能不可接受。
5. 輔助資料無法補救：`line_modes.csv` 沒有標籤且分布與 labeled 資料幾乎不重疊；`line_channels.csv` 沒有故障標籤，也沒有可對應的鍵。

## 如果仍要往可上線的方向走

1. 收集多個獨立的故障事件，跨不同班次、設備與月份，且每個事件都要包含故障前的正常窗口。
2. 明確定義預測目標與時間窗，例如「10 分鐘內是否會故障」。
3. 使用 event-based 或 strictly time-based 切分，不能隨機切分。
4. 以 precision、recall、每千筆誤報數、預警提前時間與成本矩陣選門檻，不要只看 AUC。
5. 先做 shadow mode 或離線監控，不要直接接管產線控制。
6. 若只需要「當下狀態偵測」，可先建立簡單規則 baseline；但目前連 `temp_c > 67` 這種規則在後段正常資料都會誤報 26.4%，仍需獨立事件驗證。

## 輔助資料的處理決定

- `data/line_modes.csv`：723 筆，沒有 `fault` 標籤；`firmware_ver` 固定為 3.0、`sample_period_s` 固定為 0.5，沒有資訊量。所有 723 筆至少有一個特徵超出 labeled 資料的 1–99% 範圍，屬於明顯的 out-of-distribution 資料，因此沒有拿來訓練或驗證。
- `data/line_channels.csv`：800 筆、11 個未命名通道，沒有 `fault` 標籤，也沒有 `record_id` 之類的對應鍵，無法和 `line_faults.csv` 對齊，因此沒有使用。
